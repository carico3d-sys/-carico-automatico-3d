4. SISTEMA DI AUTO-AVVIO (systemd)
-------------------------------------

  Al boot della VM, systemd avvia automaticamente 3 servizi:

  Servizio 1 - Docker:
  File: /usr/lib/systemd/system/docker.service (di default Ubuntu)
  Cosa fa: avvia il demone Docker
  Comando: sudo systemctl start docker
  Verifica: sudo systemctl status docker

  Servizio 2 - Cloudflared (tunnel persistente):
  File: /etc/systemd/system/cloudflared.service
  Cosa fa: tunnel Cloudflare con token fisso (URL stabile)
  Comando: sudo systemctl start cloudflared.service
  Verifica: sudo systemctl status cloudflared.service

  Servizio 3 - QuickTunnel (tunnel temporaneo):
  File: /etc/systemd/system/quicktunnel.service
  Cosa fa: tunnel trycloudflare (URL diverso ad ogni riavvio)
  Comando: sudo systemctl start quicktunnel.service
  Verifica: sudo systemctl status quicktunnel.service

  NOTA: i file unit di cloudflared.service e quicktunnel.service sono
  versionati in ops/ (insieme a carico3d-cleanup.service) e si installano
  sulla VM con:
    sudo bash ops/installa_tunnel.sh
  Il token del tunnel persistente va messo in /etc/default/cloudflared
  (riga TUNNEL_TOKEN=...), NON nel file unit. Il quicktunnel non richiede
  token: l'URL trycloudflare si trova nei log.

  Servizio 4 - Carico 3D Cleanup (pulizia processi orfani):
  File: /etc/systemd/system/carico3d-cleanup.service
  Cosa fa: uccide processi orfani (cloudflared, Python, gunicorn,
           qcluster) e libera le porte PRIMA che Docker parta.
  Esecuzione: si esegue UNA VOLTA al boot, poi termina.
  Verifica: sudo systemctl status carico3d-cleanup
  Log: sudo journalctl -u carico3d-cleanup --no-pager
  Installazione: sudo bash ops/installa_cleanup.sh

  I container Docker (postgres, web, worker, nginx) partono grazie
  al policy "restart: unless-stopped" in docker-compose.yml.
  Quando Docker si avvia, riavvia automaticamente i container attivi.


5. FLUSSO DI AVVIO AL BOOT
-----------------------------

  VM si accende
    ├── 1. carico3d-cleanup.service (PRIMA)
    │     └── Pulisce: cloudflared orfani, Python, gunicorn, qcluster
    │         Libera: porte 8000/5432
    │         (si esegue una volta e termina)
    │
    ├── 2. docker.service (DOPO la pulizia)
    │     └── Docker avvia i 4 container (postgres, web, worker, nginx)
    │           └── docker-entrypoint.sh esegue: migrate + collectstatic
    │
    ├── 3. quicktunnel.service
    │     └── cloudflared → tunnel verso trycloudflare.com
    │
    └── 4. cloudflared.service
          └── cloudflared → tunnel con token (se configurato)

  URL accessibili dopo il boot:
  - http://127.0.0.1/             → landing page
  - https://xxxx.trycloudflare.com/ → landing via tunnel
  - http://127.0.0.1/workspace/   → workspace (dopo login)
  - http://127.0.0.1/admin/       → admin Django

6b. PULIZIA PROCESSI ORFANI (carico3d-cleanup.service)
-------------------------------------------------------

  Problema: quando la VM si riavvia o crasha, possono restare:
  - Container Docker orfani (web, postgres, worker)
  - Processi cloudflared (tunnel) che bloccano le porte
  - Worker Django Q2 con codice vecchio che processa dalla coda
  - Processi Python/gunicorn fantasma sulla porta 8000

  Soluzione: il servizio systemd carico3d-cleanup.service pulisce
  tutto PRIMA che Docker parta, evitando conflitti.

  Installazione (una tantum, dalla cartella del progetto):
  sudo bash ops/installa_cleanup.sh

  Comandi manuali:
  sudo bash ops/vm_cleanup.sh cleanup   # Pulisci processi orfani
  sudo bash ops/vm_cleanup.sh status    # Mostra processi sospetti
  sudo bash ops/vm_cleanup.sh start     # Pulisci + avvia stack Docker
  sudo bash ops/vm_cleanup.sh stop      # Ferma tutto

  Verifica servizio:
  sudo systemctl status carico3d-cleanup
  sudo journalctl -u carico3d-cleanup --no-pager

  Disabilitare (se non serve):
  sudo systemctl disable carico3d-cleanup

  Cosa pulisce (4 passi, vedi ops/vm_cleanup.sh):
  1) Container Docker orfani (web, postgres, worker, nginx)
  2) Processi cloudflared (tunnel) fuori da Docker
  3) Processi Python orfani: manage.py (runserver, qcluster), gunicorn
  4) Porte 8000/5432 bloccate da processi fantasma

  Ogni passo è idempotente: eseguirlo due volte non crea danni.
  Il servizio systemd si esegue UNA VOLTA al boot e termina.
  Non resta in ascolto: pulisce e passa il testimone a Docker.

10. POSTGRESQL (come funziona)
-------------------------------

  PostgreSQL e' un container Docker con volume dedicato (carico3d_pgdata).
  I dati del database SONO PERSISTENTI:
  - docker compose up -d --build   → dati preservati
  - docker compose down            → dati preservati
  - docker compose down -v         → ATTENZIONE: cancella tutto

  Il migrate parte automaticamente al rebuild (docker-entrypoint.sh).
  Per farlo manualmente:
  docker compose exec web python manage.py migrate --noinput

  Verifica connessione PostgreSQL:
  docker compose exec web python manage.py dbshell
  (se apre la shell psql, il DB funziona)

  Backup del database:
  docker compose exec -T postgres pg_dump -U carico carico_3d > backup_$(date +%Y%m%d).sql

  Ripristino backup:
  docker compose exec -T postgres psql -U carico carico_3d < backup_20260822.sql

13. TROUBLESHOOTING (errori comuni)
-------------------------------------

  Errore "Permission denied" su SSH:
  ssh -p 2222 gianni@127.0.0.1
  (inserire password: gianni)

  Errore "not a git repository":
  find /home -name "manage.py" -type f 2>/dev/null
  cd /percorso/trovato

  Container non parte dopo rebuild:
  docker compose logs web --tail=100

  PostgreSQL non risponde:
  docker compose exec web python manage.py dbshell
  Se da errore: docker compose ps postgres

  Tunnel non funziona:
  sudo systemctl status quicktunnel.service
  sudo journalctl -u quicktunnel.service --no-pager -n 20
  Riavvia: sudo systemctl restart quicktunnel.service

  Docker non parte:
  sudo systemctl status docker
  sudo systemctl start docker

  Pagina non si aggiorna nel browser:
  Ctrl + Shift + Delete → Cancella cache
  Oppure Ctrl + F5 (hard refresh)
  Oppure finestra di navigazione in incognito

  .env mancante:
  cp .env.example .env
  nano .env

  Worker Q2 non funziona (task ottimizzazione restano in coda):
  docker compose logs worker --tail=50
  docker compose restart worker

  Kernel panic / crash VM:
  Riavvia la VM da VirtualBox (chiusura forzata)
  Dopo il riavvio, Docker parte in automatico
  Verifica: docker compose ps


14. ARCHITETTURA
-----------------

  Windows (PC locale) → GitHub (branch auto_7_1) → Ubuntu VM (produzione)

  Flusso:
  1. Da Windows: git push origin auto_7_1
  2. Da SSH nella VM: git pull origin auto_7_1
  3. Da SSH nella VM: docker compose up -d --build

  Docker Compose Stack (4 container):
  - postgres   → database PostgreSQL (volume: carico3d_pgdata)
  - web        → Django + gunicorn (porta interna 8000)
  - worker     → Django Q2 (task asincroni ottimizzazione)
  - nginx      → reverse proxy (porta 80 esterna)

  Systemd Services (auto-start al boot):
  - carico3d-cleanup.service → pulizia processi orfani PRIMA di Docker
  - docker.service           → demone Docker
  - quicktunnel.service      → tunnel trycloudflare (URL diverso ogni riavvio)
  - cloudflared.service      → tunnel con token (URL fisso)

  Volumes Docker (persistenti):
  - carico3d_pgdata      → dati database
  - carico3d_staticfiles → file CSS/JS collectstatic
  - carico3d_appdata     → icone config + immagini upload

  URL:
  http://127.0.0.1/                  → landing page (locale)
  https://xxxx.trycloudflare.com/    → landing page (tunnel)
  http://127.0.0.1/workspace/        → workspace (dopo login)
  http://127.0.0.1/admin/            → admin Django
